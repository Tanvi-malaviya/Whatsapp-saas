Sathwara WhatsApp SaaS — Module-wise Development Specification
Oct 12, 2026 · @Bhavesh Sathwara
How to use this document
Build 15 modules in 6 phases; only Modules 0–4, 12 (Super Admin) and 13 (managed setup) are needed for the first paid launch of Bot Starter. Each module lists what to build, the data it owns, the APIs and background jobs it needs, and a line-by-line Take care checklist. Tick a checklist line only when it is implemented and tested.
Scope source: Sathwara InfoTech WhatsApp SaaS Business & Implementation Plan v1.0 (12 Oct 2026), updated with Meta changes current as of this date.
Platform scope (this release): web app only — a responsive web application for desktop, tablet and mobile browsers. No native mobile app is built now.
Facts that shape the whole build
Meta path: Sathwara joins as a Meta Tech Provider. Customers onboard through Embedded Signup v4 and pay Meta directly for messages. Embedded Signup v2 is deprecated on 15 Oct 2026; build only on v4 and ignore older code samples.
Meta pricing (India, from 1 Oct 2026): service replies get 1,000 free per number per month, then are charged; utility templates are charged even inside the 24-hour window; marketing is about 7–8× utility. The product must show customers an estimated Meta cost.
AI policy: from 15 Jan 2026 Meta bans general-purpose AI assistants on the Business API. Our AI must answer only from each customer's own business knowledge and escalate everything else.
Legal entity: Sathwara InfoTech is a sole proprietorship (Udyam registered). Business name must match exactly across Meta, Razorpay, invoices and the website.
Privacy law: IT Act SPDI Rules 2011 apply now; DPDP Act operational duties apply from mid-May 2027. Build to DPDP from day one. CERT-In: report incidents within 6 hours; keep logs 180 days in India.

Take care
☐ Choose India as the VPS location when buying; Hostinger lists India among its VPS locations. Note it in the sub-processor list.
☐ Use Laravel's Storage facade for every file (never raw paths), so moving media to S3-compatible object storage later is only a config change.
☐ Serve files only through a controller with permission checks and temporary signed URLs.
☐ Media fills the disk first: apply the message retention setting (Module 3), compress images, alert at 80% disk used, and plan a move to object storage when the disk passes 70%.
☐ Bind PostgreSQL and Redis to localhost only; no database or Redis port open to the internet.
☐ Firewall (UFW) open only on 22, 80 and 443; SSH keys only, root password login off; fail2ban on SSH and Nginx.
☐ Automatic security updates (unattended-upgrades) with a planned monthly reboot window.
☐ Sync the server clock with NTP; CERT-In expects synchronised clocks on logs.
☐ Keep logs 180 days with logrotate; compress old logs and include them in backups.
☐ Hostinger backups stay with the same provider: also keep your own encrypted nightly copy outside the production VPS, and test a full restore before launch and every quarter.
☐ Take a manual Hostinger snapshot before every production deploy, so a bad release rolls back in minutes.
☐ Supervisor restarts Horizon queues and Reverb automatically after a crash or reboot.
☐ Run Reverb WebSockets behind Nginx on wss:// using the same SSL certificate.
☐ Set SPF, DKIM and DMARC for the domain in Hostinger DNS before sending any email; check with a mail-tester.
☐ Send every email through a queued Mailable with a rate limiter that stays under the mailbox's daily cap; log each send and bounce.
☐ Use Hostinger Mail only for system emails (verification, invites, invoices, alerts, digests); never for customer marketing or bulk mail.
☐ Keep the mail settings in .env; if volume nears the cap, add mailboxes or switch to a transactional email service without code changes.
☐ One VPS is a single point of failure: do not promise an uptime SLA, and keep the restore runbook ready.

Conventions used in every module
Every table has organization_id (except global tables) and every query is scoped by it.
Every money amount is stored in paise as an integer, with a currency column.
Every timestamp is stored in UTC; displayed in the workspace's timezone (default Asia/Kolkata).
Every external call (Meta, Razorpay, AI) goes through one service class with retries, timeouts and logging.
Every user-visible action that changes data writes an audit_logs row.
Feature access is checked on the server through Entitlements::can($org, 'feature.key'), never only by hiding UI.
Module architecture (web app)
The web app is one Laravel modular monolith: 15 modules in one codebase and one database (the diagram shows the 14 built first; the agency portal comes later), with hard boundaries enforced by tests. Product modules never call Meta or Razorpay directly; they go through four core modules, so every rule about windows, consent, entitlements and billing lives in one place.
web app architecture · modules, workers, data, external services
Meta and Razorpay send webhooks to the entry points; all outgoing calls leave from the core modules only. Everything except the external services runs on one Hostinger VPS in India.
Dependency rules
Core modules (Foundation, Billing, Meta connection, Messaging engine) never depend on product modules.
Product modules depend only on core modules and on the CRM contact service.
Only Meta connection and Messaging engine call the Meta Graph API; only Billing calls Razorpay; only AI Assistant calls the AI provider. Enforced by Pest arch() tests.
Every send — bot, agent, campaign, workflow, booking, AI — goes through Messaging\SendMessage, which runs the pre-send checks.
A module owns its tables. Other modules read them through the owner's service class, never by querying another module's models.
Side effects between modules use events (table below), not direct calls, so a failing listener cannot break the sender.
Every controller, job and listener reads the organization from TenantContext; jobs carry organization_id and restore it before running.
Every product route group has entitlement middleware, e.g. ->middleware('entitled:inbox').
UI pages only use components from resources/js/Components/ui (the design system).

Life of an inbound message
Meta posts to /webhooks/meta; signature verified; raw payload saved to webhook_inbox; 200 returned.
ProcessMetaWebhook job (queue webhooks) finds the organization by phone number ID and dedupes by wamid.
Messaging stores the contact, conversation and message, updates the 24-hour window, and raises InboundMessageReceived.
Inbox pushes the message to agents through Reverb.
Bot (queue bot) decides the reply and calls SendMessage with key = inbound wamid.
SendMessage runs the pre-send checks, calls Meta, stores the wamid of the reply.
Status webhooks later update the reply to delivered / read and feed the Meta cost estimate.
Web app design rules
One design system for every screen, so a shop owner on a phone browser and an agent on a laptop both understand the app without training. Build these as shared components first; module screens only assemble them.
Principles
Plain language first. Business owners, not developers, use this app. “Connect your WhatsApp number”, not “Provision WABA”.
Show the state of WhatsApp at all times. Connection status and Meta cost estimate are always one click away.
Safe by default. Anything that sends to many people or costs money asks for confirmation and shows the impact first.
Every screen has a next step. Empty, error, locked and limit states always tell the user what to do.
Same thing, same look. One button style, one status colour per meaning, one way to confirm.
App shell and navigation
Left sidebar (desktop): Dashboard, Inbox, Contacts, Bot, Campaigns, Automation, Bookings, AI Assistant, Reports, Settings. Modules not in the plan show a lock icon and open an upgrade page, never a broken screen.
Top bar: workspace switcher, WhatsApp connection status pill, notifications bell, help, user menu.
Settings sections: Workspace, Team & roles, WhatsApp connection, Billing & plan, Integrations & API, Privacy & data, Audit log.
Content area: max width 1280 px for forms and lists; Inbox and Kanban use full width.
Breadcrumbs on pages deeper than two levels; page title + one primary action at the top right.
Setup checklist on the Dashboard until onboarding is done: verify email → connect WhatsApp → set up bot → send test → go live.

Module 0 — Platform foundation (tenancy, auth, roles, audit)
Every other module depends on this one; a mistake here leaks one customer's chats to another. Build it first, test it hardest.
What to build
Sign up with email + password, email verification, login, logout, forgot/reset password.
Optional login with Google; optional two-factor authentication (TOTP) — mandatory for Owner and Super Admin.
Organization (workspace) creation after signup: business name, industry, timezone, country, GSTIN (optional), billing address.
One user can belong to many organizations; an organization switcher in the header.
Invitations by email with role, expiry (7 days), resend and revoke.
Roles: Owner, Admin, Agent, Viewer, Billing. Custom roles later.
Permission matrix per module (e.g. inbox.reply, campaign.send, billing.manage).
Audit log viewer for Owner/Admin.
Session list with “log out other devices”.
Account and workspace deletion requests (soft delete + 30-day purge).
Data
users, organizations, organization_members (user_id, organization_id, role_id, status), roles, permissions, role_permissions, invitations, sessions, audit_logs (actor, organization, action, target_type, target_id, ip, user_agent, before/after JSON, created_at), login_attempts.
Take care
☐ Add a global query scope so every tenant model is filtered by organization_id automatically.
☐ Resolve the current organization from the session on the server, never from a request parameter the browser can change.
☐ Use UUIDs or ULIDs for public IDs so records cannot be guessed by incrementing numbers.
☐ Write an automated test: user of Org A requests every Org B route and gets 404, never data.
☐ Consider PostgreSQL row-level security as a second safety net for the most sensitive tables (messages, contacts).
☐ Hash passwords with bcrypt/argon2; never log passwords or tokens.
☐ Rate-limit login, signup, password reset and OTP (e.g. 5 attempts per 15 minutes per IP + email).
☐ Lock out or add CAPTCHA after repeated failed logins.
☐ Make email verification required before connecting WhatsApp or paying.
☐ Invitations: single-use token, expire after 7 days, bind to the invited email address.
☐ Prevent removing or downgrading the last Owner of an organization.
☐ Check permissions in controllers/policies, not only in menus.
☐ Write audit logs for: role changes, invites, WhatsApp connect/disconnect, billing changes, exports, deletions, API key creation.
☐ Make audit logs append-only (no update/delete from the app).
☐ Store all timestamps in UTC; convert for display only.
☐ Regenerate the session ID on login; set cookies Secure, HttpOnly, SameSite=Lax.
☐ Enable CSRF protection on all forms; set security headers (HSTS, CSP, X-Frame-Options).
☐ Keep a deleted_at soft delete for organizations, then purge personal data after the retention period.
☐ Record consent to Terms of Service and Privacy Policy with version and timestamp at signup.
☐ Add a basic Super Admin “impersonate” feature only with audit logging and a visible banner (see Module 12).
Module 1 — Products, plans, entitlements and billing
Sathwara bills only for software and setup; Meta bills the customer for messages. This module turns a payment into feature access, and must never grant access on a browser redirect alone.
What to build
Product catalogue managed by Super Admin: products (modules), plans, prices, billing interval (monthly / yearly), GST rate.
Plan limits as data, not code: agents, contacts, workflows, active templates, campaigns per month, AI answers per month, phone numbers.
Entitlement engine: can() for features, remaining() for limits, consume() for usage.
Public pricing page fed from the same catalogue.

Billing page: current plan, add-ons, next renewal date, payment method, invoices, usage vs limits.
Upgrade / downgrade / add module / cancel at period end / reactivate.
Proration rules for upgrades (charge difference immediately) and downgrades (apply at next renewal).
Failed payment flow: reminders on day 0, 3, 7; grace period 7 days; then suspend sending; data kept.
GST tax invoices (PDF + email), credit notes for refunds, invoice numbering per financial year.
Coupons / pilot discounts with expiry.
Internal financial ledger.

☐ Activate a plan only after a verified webhook or a server-side API fetch confirms payment; never on the success redirect.

☐ Handle events arriving out of order (e.g. charged before activated) by reading current state from Razorpay.
☐ Keep amounts as integers in paise; never use floats for money.
☐ Make the ledger append-only: refunds and corrections are new reversing rows, never edits or deletes.
☐ Show prices inclusive or exclusive of GST consistently, and say which on every screen.
☐ Put Sathwara's legal name, address, GSTIN (once registered), the SAC code your CA confirms for SaaS on every invoice.

☐ Use one continuous invoice number series per financial year (e.g. SIT/2026-27/0001); never reuse numbers.
☐ Check entitlements on the server in every protected API and job, including background workers.
☐ Check limits at the moment of use (e.g. adding the 4th agent on a 3-agent plan returns a clear upgrade message).
☐ On downgrade, never delete over-limit data; make extra items read-only until the customer chooses.
☐ On suspension, stop outgoing sends and automations but keep receiving and storing incoming messages.
☐ Follow RBI recurring-payment rules: show mandate details, send pre-debit notification (Razorpay does this; verify it is enabled).
☐ Show the effective date and amount before any upgrade, downgrade or cancellation is confirmed.
☐ Keep Meta message charges completely separate; never show them as Sathwara charges.
☐ Show a disclaimer on pricing: “WhatsApp messaging fees are billed by Meta directly.”
☐ Write a daily reconciliation job comparing Razorpay payments with local records; alert on mismatch.
☐ Keep Razorpay keys in environment secrets; never in the frontend or repository.
☐ Test with Razorpay test mode: success, failure, retry, refund, cancellation, halted mandate.
Module 2 — Meta / WhatsApp connection
This module connects a customer's WhatsApp Business Account (WABA) to our app through Embedded Signup v4 and keeps it healthy. It is also what Meta reviews before granting Advanced Access, so build a thin working version early.
Meta setup (one-time, Sathwara side)
Meta Business portfolio for Sathwara InfoTech, business verification complete.
Meta app with the WhatsApp use case; Tech Provider onboarding complete.
Facebook Login for Business configuration with the WhatsApp Embedded Signup variation (v4).
Permissions requested for App Review: whatsapp_business_management, whatsapp_business_messaging (and business_management only if truly needed).
App-level webhook URL + verify token; subscribe to messages, message_template_status_update, account_update, phone_number_quality_update, account_review_update, business_capability_update, template_category_update.
Sathwara's own test WABA and phone number for demos and App Review.
What to build (customer side)
“Connect WhatsApp” wizard with clear pre-checks: Facebook account, business details, a phone number not already on WhatsApp (or a WhatsApp Business App number for coexistence).
Launch Embedded Signup v4 with session logging; capture WABA ID, phone number ID and the token code.
Server-side: exchange the code for a business integration system user token; store encrypted.
Server-side onboarding steps: subscribe our app to the customer's WABA webhooks, register the phone number (PIN), verify Meta-side billing is set up by the customer.
Connection status machine: not_connected → initiated → authorization_pending → verification_pending → setup_pending → webhook_pending → testing → connected, plus action_required, restricted, disconnected.
Test step: send a message to the owner's own phone and confirm the delivery webhook arrives.
Connection health page: display name status, quality rating, messaging limit tier, account review status, last webhook received.
Business profile editor: about, description, address, email, website, profile photo.
Coexistence option (customers who keep using the WhatsApp Business App) — phase 2 of this module.
Disconnect flow with confirmation and token deletion.
Webhook receiver (shared by all modules)
One public endpoint POST /webhooks/meta that verifies the X-Hub-Signature-256 header with the app secret.
Write the raw payload to webhook_inbox and return 200 within a few hundred milliseconds.
A queued job parses each entry and routes it: messages → Module 3, template updates → Module 7, account updates → this module.
Data

Take care
☐ Use Embedded Signup v4 only; check Meta's changelog before every release.

Take care
☐ Every proposal lists limits (e.g. up to 20 FAQs, 3 menus, 5 templates) and exclusions; extra work is a change request with a price.
☐ State customer responsibilities in writing: Meta business verification, phone number, content accuracy, consent for contacts, Meta payment method.
☐ Do not start work before payment (or deposit) is confirmed by webhook.
☐ Customer authorises Meta access themselves through Embedded Signup; Sathwara never asks for Facebook passwords.
☐ Record acceptance with name, date and IP; start the support period from that date.
☐ Use the bot templates gallery (Module 4) so setups are repeatable and fast.
☐ Track time spent per setup order to check whether setup pricing is profitable.
☐ Publish support hours honestly; do not promise 24/7 or guaranteed response times yet.
Module 14 — Agency / reseller portal (Phase 6, later)
Lets agencies manage several client workspaces and optionally rebrand the platform. Build only when real demand, margins and support capacity justify it.
What to build
Agency account that owns or manages many client organizations.
Switch between client workspaces without separate logins.
Wholesale pricing and agency billing (agency pays Sathwara; agency bills its clients).
Optional white-label: custom domain, logo, colours, email sender name.
Agency-level reports across clients.
Take care
☐ Agency staff access to a client workspace is granted by the client and can be revoked by the client.
☐ Each client remains a separate tenant with its own WhatsApp connection, contacts and Meta billing.
☐ Check Meta's partner terms on whether an agency can onboard clients under Sathwara's Tech Provider app.
☐ Custom domains need automated TLS certificates and verified DNS ownership.
☐ White-label must not hide who processes the data; keep Sathwara named in the DPA.
Cross-cutting: security, privacy, reliability, infrastructure and testing
These rules apply to every module and are release gates: a module is not done until its lines here pass.
Security
☐ All secrets (Meta app secret, Razorpay keys, AI keys, DB passwords) in environment variables or a secrets manager; never in Git; add a secret scanner to CI.
☐ TLS everywhere; HSTS on; no plain HTTP endpoints.
☐ Encrypt tokens and integration credentials at the field level; encrypt backup archives before they leave the server.
☐ Run dependency vulnerability checks (Composer / npm audit) in CI weekly.
☐ Protect against OWASP Top 10: SQL injection (ORM / bindings), XSS (escape output, CSP), CSRF, SSRF (webhook URLs), insecure file upload.
☐ Least-privilege database users: the app user cannot drop tables.
☐ Server hardening: SSH keys only, no root login, firewall open only on 80/443, automatic security updates.
☐ Rotate secrets on staff change and at least yearly; document how.
☐ External security review / penetration test before scaling beyond pilots (Phase 5–6).
Privacy (IT Act SPDI Rules now, DPDP Act from May 2027)
☐ Publish Privacy Policy, Terms of Service, Acceptable Use Policy, Refund & Cancellation Policy, and a Data Processing Agreement before the first pilot.
☐ Sathwara is a Data Fiduciary for its own customers' account data and a Data Processor for their contacts and chats; the DPA says so.
☐ Keep a list of sub-processors (Hostinger for server, storage and email; Razorpay; AI provider) and share it with customers.
☐ Collect only the data each feature needs; no Aadhaar, card numbers or health details in free fields.
☐ Provide per-organization data export and full deletion on cancellation (after a stated retention period, e.g. 30 days).
☐ Provide per-contact export and deletion to support data principal requests.
☐ Name a grievance contact (Bhavesh initially) on the website with an email address; respond within the legal timeline.
☐ Breach plan: detect, contain, inform affected customers, report to CERT-In within 6 hours of noticing a reportable incident, and later to the Data Protection Board when DPDP duties start.
☐ Keep application and security logs for 180 days on India-region infrastructure (CERT-In direction).
☐ Keep the database, files and backups on Hostinger servers located in India.
Reliability
☐ Every Meta and Razorpay webhook: verify signature → store raw → return 200 → process in queue → dedupe by event ID.
☐ Separate queues by priority: webhooks > bot > inbox > workflows > campaigns > reports.
☐ Failed jobs go to a failed-jobs table with alerting; no silent drops.
☐ Hostinger VPS backups plus your own nightly encrypted pg_dump and files archive stored off the production VPS; keep 30 days.
☐ Test a full restore to a separate server at least once before launch and then quarterly.
☐ Health checks and uptime monitoring on the app, webhook endpoint, queues and database.
☐ Alerts for: webhook 5xx, queue delay above 1 minute for bot queue, send error rate spike, payment webhook failures, disk above 80%.
☐ Write a one-page incident runbook: who is contacted, how customers are informed, how to roll back.
☐ Zero-downtime deploys on the VPS (release folders with a symlink switch, e.g. Deployer or Laravel Envoy; take a Hostinger snapshot first); run migrations safely.
☐ Keep staging and production separate, with separate Meta apps or test numbers and Razorpay test keys.
Testing
☐ Unit tests for entitlement checks, window rules, bot matching order, consent and suppression logic.
☐ Feature tests for tenant isolation on every route group.
☐ Replay tests: feed recorded Meta webhook payloads (duplicates, out-of-order) and check final state.
☐ Razorpay test-mode tests for every billing scenario.
☐ Load test the webhook endpoint and sending engine (e.g. 50 messages per second) before campaigns launch.
☐ End-to-end test on a real test number before each release: connect, receive, bot reply, handoff, agent reply, template send.
☐ Manual QA checklist on mobile browsers, since many Indian SMB owners use phones.
The full condition-by-condition test catalogue is in the Testing section below.
Notifications (shared service)
Many modules say “notify the Owner” or “notify the agent”; one shared service does all of it, so users control it in one place.
☐ Channels: in-app bell (realtime), email, browser push. WhatsApp alerts to staff only after the staff member opts in.
☐ Notification types with a default channel each: handoff, mention, assignment, payment failed, connection restricted, campaign paused, import finished, export ready, reminder due.
☐ Per-user preferences page: turn each type on or off per channel; critical ones (payment failed, number restricted) cannot be turned off for Owners.
☐ Group bursts (e.g. 20 handoffs in 5 minutes → one email digest) to avoid spamming.
☐ Every email has an unsubscribe-from-this-type link and the workspace name in the subject.
☐ Notifications are tenant-scoped and permission-checked: an agent never gets alerts about conversations they cannot see.

Build order, sprint plan and App Review readiness
Build in this order and do not start a phase until the gate above it passes; only Phase 2 earns money, so everything before the pilot serves it. Dates are planning targets for a small team and move with Meta approval time.
build roadmap · 6 phases, 5 gates
Phases 1 and 2 overlap on purpose: a thin Embedded Signup + webhook + reply flow is needed by week 5 for the App Review video.
First 12 weeks, two-week sprints
Sprint 1 (weeks 1–2): repo, CI, buy Hostinger KVM 2 (production) and KVM 1 (staging) in India, harden servers, set up Hostinger Mail with SPF/DKIM/DMARC; Module 0 auth, organizations, roles, invitations, audit log; Meta app created, business verification submitted.
Sprint 2 (weeks 3–4): Module 1 catalogue, entitlements, Razorpay test-mode subscriptions and setup orders, invoices; webhook receiver + webhook_inbox; Meta test number sending and receiving.
Sprint 3 (weeks 5–6): Embedded Signup v4 flow + server-side onboarding + connection status machine; sending engine with pre-send checks; record App Review video and submit.
Sprint 4 (weeks 7–8): Module 4 bot (welcome, keywords, FAQs, menus, hours, fallback, handoff, opt-out, test console, logs); minimal inbox to read and answer handed-off chats; Super Admin basics.
Sprint 5 (weeks 9–10): Module 13 setup orders and proposals; onboard 2–3 pilot businesses with managed setup; Razorpay live mode.
Sprint 6 (weeks 11–12): fix pilot issues, help centre, monitoring and alerts, backup restore test, launch Bot Starter self-service when all launch gates pass.
